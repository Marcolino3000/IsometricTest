## Project

Turn-based isometric tactics prototype (part of **DuxAeternus**). Unity **6000.3.11f1**, URP, new Input System, Odin Inspector, Singularity Hot Reload. Repo root holds the Unity project in `IsometricTest/`; the single scene is `IsometricTest/Assets/Scenes/SampleScene.unity`.

## Assemblies and compiling

There are **no asmdefs under `Assets/`** — everything compiles into the default `Assembly-CSharp` (runtime) and `Assembly-CSharp-Editor` (anything under an `Editor/` folder). The only asmdefs are in `Packages/com.duxaeternus.imtoolkit` and the Odin math module.

`Core.csproj`, `Data.csproj`, and `Gameplay.csproj` are **stale leftovers** with no matching asmdefs — ignore them. `Assembly-CSharp.csproj` is authoritative.

### Compile-check without launching Unity

Verified working. Run from `IsometricTest/` (the folder holding the `.csproj` files):

```bash
grep -oE "<HintPath>[^<]+</HintPath>" Assembly-CSharp.csproj | sed -E 's#</?HintPath>##g' | awk '{print "-r:\"" $0 "\""}' > /tmp/refs.rsp && echo '-r:"Library/ScriptAssemblies/DuxAeternus.ImToolkit.dll"' >> /tmp/refs.rsp && grep -oE '<Compile Include="[^"]+"' Assembly-CSharp.csproj | sed -E 's#<Compile Include="##; s#"$##' | sed 's#\\#/#g' | sed 's/^/"/; s/$/"/' > /tmp/srcs.rsp && csc -nologo -nostdlib+ -noconfig -target:library -langversion:latest -out:/tmp/check.dll @/tmp/refs.rsp @/tmp/srcs.rsp
```

Use `Assembly-CSharp-Editor.csproj` for editor scripts. Notes: the `.csproj` is regenerated by Unity and will not list brand-new files, so append them to the source list explicitly; runtime scripts are interdependent, so compile the full list in one go. `csc` lives in `/Library/Frameworks/Mono.framework`; **zsh does not word-split unquoted vars**, so quote source paths individually. ## Architecture

### Composition root

`Runtime/Core/Initiator.cs` is a **manual DI root** — no framework. Its `Awake()` runs `SetupReferences()` → `SpawnEntities()` → `SetupUI()` → `StartGame()`, wiring every system through explicit `Setup(...)` calls in a deliberate order. Systems are `MonoBehaviour` singletons on a Systems prefab, referenced via `[SerializeField]`. When adding a system, wire it here — **order matters**, since `Setup` is also where event subscriptions happen.

`Restart()` (context menu) deliberately skips `SetupReferences`/`SetupUI` so persistent singletons don't re-subscribe. Anything created at runtime instead of in the scene (`AttackPreview`, floating text) is built in `SetupReferences`.

### Turn state

`Core/State/GameStateManager.cs` owns a tiny `State` (active `Team`, `UnitsHaveActionsLeft`) and emits `ChangeEvent<T>` (previous + new snapshot, both cloned). Three events, and the split is load-bearing:

- **`TurnReset`** — phase 1, fires only on an actual team change. Per-turn world prep: AP refresh, fog/direction recompute, selection clear. Anything the turn's actor depends on subscribes here.
- **`TurnStarted`** — phase 2, immediately after; the turn is live and the AI may act.
- **`GameStateChanged`** — every change including mid-turn (e.g. `SetActionsLeft`), for observers mirroring state regardless of turn boundaries.

`Core/State/Direction.cs` is **static mutable state** rebound on every `TurnReset` — `Forward` means the active team's forward. Reading it outside the active turn is meaningless.

### Selection → action pipeline

This is the main input path, and it is data-driven rather than imperative:

```
InputHandler → Raycaster → Clickable (IClickable: Unit | Tile)
   → Selector  … folds hover/click/selection into a single SelectionStatus enum
   → ActionAssigner  … switch on SelectionStatus
   → ActionExecutor  … plan / test / execute
```

`Selection` (in `Selector.cs`) recomputes `Status` in `UpdateStatus()` on **every property setter** via a C# pattern-match over the `(selectedUnit, clickedUnit, hoveredUnit, hoveredTile)` tuple. Click fields are set, an event fires, and they are immediately nulled — clicks are one-shot pulses, hovers are sticky. To add an interaction, add a `SelectionStatus` case rather than special-casing elsewhere.

### Actions: plan then execute

Actions are ScriptableObject-authored and instantiated per use:

- `ActionData<UCondition, TEffect>` (SO, e.g. `AttackActionData`) holds a `Condition` SO (cost, range) + `Effect` SO, and `CreateAction(context)` returns a runtime `UnitAction<UCondition, TEffect>` implementing `IUnitAction { Cost, TestConditions(), ExecuteEffects() }`.
- `ActionExecutor` (one per unit) builds a `List<IUnitAction>` plan — a move is one action *per tile step*, so per-step terrain cost is respected — then `TestConditionsForPlannedActions()` returns the index of the first failing step, which drives the path highlighting (the reachable prefix renders differently from the unreachable tail).
- Hover plans and previews; click re-plans and executes. `PlanAttackAction` uses `GetAttackApproachPath`, which stops at the first tile the unit could actually strike from (`CombatRules.CanAttackFrom` — range *and* line of fire), so a ranged unit stops short instead of walking adjacent, and walks on around a mountain instead of halting behind it with the target in range and no shot at it. The plan's `ActionContext.FromTile` is that tile, and `AttackAction.TestConditions` asks the same question of it — the path and the condition can never disagree because they are the same call. It replaced a precomputed `Distance`, which measured from one tile while the range was read off another.

Callers can hold a unit past its death, so plan methods **guard `unit` and `TargetUnit` with `IsAlive`** (plus a null check) before touching plain-C# state. Keep that guard on new action paths. Dead units are *hidden, not destroyed* — see Undo/redo below — so a plain null check is not enough.

Every executed action announces itself through `ActionReporter.Report(...)` at the end of the `Execute*` method. New execute paths should do the same, or they will not be undoable.

### Traits: the extensibility seam

`Gameplay/Traits/` — `Trait : ScriptableObject` with five no-op virtuals: `ModifyOutgoingDamage`, `ModifyIncomingDamage`, `ModifyAttackRange`, `ModifySightRange`, `ModifyMoveCost`. Split into `UnitTrait` (travels with the unit, listed on `UnitState.Traits`) and `TerrainTrait` (attached to terrain, applies to whoever stands there) purely so inspector lists stay type-correct.

`EquipmentTrait` is the workhorse on the unit side: one asset with a flat `DamageBonus` / `DefenseBonus` / `RangeBonus`, one per hook. Gear usually moves more than one of those numbers, so most passive items need no new class — reach for it before writing another `UnitTrait`.

**Item synergy lives in `EquipmentTrait.RequiresWeapon`.** Only one passive can be worn, so a passive cannot pay off another passive — but it can pay off the weapon that is drawn, and that is a real choice because both weapon slots keep their contents and swapping is free. `WeaponRequirement.Any | Melee | Ranged` gates all three bonuses on `UnitState.AttackAction.Kind`; which unit carries the trait differs per hook (attacker deals, defender takes), so `AppliesTo` is passed the right one rather than guessing. The other synergy axis is terrain, which is `TerrainDamageTrait` on the unit side and `TerrainTrait`s on the tile. A `UnitTrait` can also sit on the weapon itself (`AttackActionData.Traits`, see Items and weapons), which is where a trait that *is* the weapon belongs rather than a passive gated on holding it.

`Gameplay/Global/CombatRules.cs` is the single place these fold together — pure math, no side effects, shared by the combat resolver, `AttackAction.TestConditions`, the planner and the attack preview so they always agree. `CanAttackFrom(attacker, fromTile, targetTile)` is the whole "could it strike" question — effective range plus `SightRules.HasClearLine` — asked by the attack condition, the approach path, the threat overlay and the AI; `CanRetaliate` asks for the line too, so high ground can answer a shot that cannot be answered back. Traits see an immutable `CombatContext` (a strike; retaliation is its own strike with roles swapped and `IsRetaliation` set) or `RangeContext`.

**Route every rule number through a `CombatRules`-style query function.** A new mechanic should be a new SO asset plus at most one new trait/effect class — never a switch case in `ActionAssigner` or a new per-type `Plan*`/`Execute*` pair on `ActionExecutor`.

`CombatRunner.ResolveCombat` applies damage, asks `CombatRules.CanRetaliate` whether the defender strikes back, then removes the dead.

`Gameplay/Global/MovementRules.cs` is the same idea for the other half of a turn: `GetStepCost` / `GetPathCost` fold the base move cost, the tile's `ExtraMoveCost` and every trait's `ModifyMoveCost`, clamped so **a step is never free** (a free step would cross the map, since `MoveAction` only tests cost against AP). Four things used to compute this separately and drift — `Pathfinder` picking a route, `TileSpawner.GetMoveableTiles` deciding what is in reach, `AiController` budgeting, `MoveAction.Cost` charging. They all ask here now, so a discount changes the route, the highlight, the AI's plan and the bill together. `Pathfinder.FindPath` takes an optional `UnitState mover` for that reason; `GetMoveableTiles(UnitState)` takes the state instead of a position/AP/cost triple. `CombatRules.TraitsAffecting(UnitState, Tile)` is public so both rule sets fold the identical trait set.

`Gameplay/Global/SightRules.cs` is the third of them, for the half of a turn that is neither fighting nor walking. **Two questions, deliberately apart.** `GetSightRange(Unit)` / `(Unit, Tile)` folds every trait's `ModifySightRange` over `Unit.SightRange` — which is now a *base*, the way `Condition.Range` is a weapon's, so nobody reads it for what a unit actually sees. `BlocksSight(blocker, viewer)` is the other: terrain hides what lies behind it only from somebody standing **lower** than it (`Tile.Elevation`, authored per `TerrainProfile` — flat 0, hills 1, mountains 2), so a unit on a hill looks over the hills and is stopped only by the mountains. Kept apart because reach belongs to whoever looks and blocking belongs to the ground in between: a unit does not carry the hill it is hiding behind, so blocking can never be a trait.

`HasClearLine(from, target)` walks that line tile by tile and is the **one** line an eye and an arrow both travel — an archer cannot shoot through the mountain it cannot see through. Sampled once per step along the longer axis, so neither end is ever tested (a hill is seen and shot *at* from below; only what stands behind it is not), which also leaves melee alone without a case for it: adjacent tiles have nothing in between. It is the only rule query that cannot answer from its arguments alone, so the Initiator injects the `TileSpawner` (`SightRules.Setup`, right after `CombatRules.Setup`); without one it blocks nothing rather than blinding the game.

`Tile.Elevation` is **not** `HeightOffset` — how high a tile is drawn and what can be seen over it are authored separately, so a visual tweak never moves a rule. Hills grant sight through an ordinary terrain trait (`SightBonusTrait`, asset `Resources/Traits/Hill Sight.asset`, on `HillTerrain.Traits`), which is what makes "hills see further" and "hills see over" one asset and one number each rather than a special case.

`Gameplay/Global/GameRules.cs` (SO, asset at `Resources/Settings/Default GameRules.asset`, injected into `CombatRules` as the *first* line of `Initiator.SetupReferences`) holds match-wide switches that belong to no unit or tile — `RetaliationEnabled`, read by `CombatRules.CanRetaliate` (rule first, then effective range), `ShowEnemyTurns` and `HideUnexploredTerrain`, both read by `FogOfWar` (see Fog below), `StackDuplicateActiveItems`, read by `ItemManager.CanStack` (see Items), `AutoCollectLootboxes`, read by `LootSpawner` (see Loot below), and the four win/loss switches read by `VictoryRules` (see Winning and losing). It is held as a live reference, so toggling it in the inspector applies mid-play. Rules that *do* belong to a unit or tile stay traits.

`Gameplay/Global/CombatLog.cs` is the debugging counterpart to `CombatRules`: `GameRules.LogCombatCalculations` (same asset, so it toggles mid-play) prints **one console message per attack**. `CombatRules.CalculateDamage` folds step by step for that reason; `CombatRunner` brackets the exchange with `BeginAttack`/`EndAttack` so a counter-strike reads under the strike that caused it.

**Two switches, and the line between them is "did it move a number".** `LogCombatCalculations` writes the arithmetic and its causes only — base weapon damage, every trait that changed the number with the value before and after, the total, the health left, why nobody struck back, who fell. `LogCombatDetails` adds what surrounds those numbers — the tiles and the distance, what a trait rolled (crit chances), and the traits that were asked and changed nothing. Anything new goes on the side of that line it belongs to; `CombatLog.Details` is the query, and a caller that builds its own message asks it *before* formatting, since whichever switch is off has to cost nothing.

**It states each fact once, and new entries should keep it that way.** Who hits whom is in the header line only — a retaliation is the same pair with the roles swapped, so it adds just its weapon; the health numbers are appended to the damage line, unnamed, since they are always that strike's target; retaliation is reported only when it *doesn't* happen (a counter-strike announces itself); traits consulted that changed nothing share one `no effect:` line, because a bonus that fails to apply is what one goes looking for but does not deserve a line each. A trait that wants to explain itself (`CriticalHitTrait` reporting its roll) calls `CombatLog.Detail` behind an `if (CombatLog.Details)` guard rather than `Debug.Log` — that is where new trait-specific tracing goes, and when the trait changed nothing that note replaces its line, so it has to name itself.

### Items and weapons

**`Gameplay/Items/Item.cs` is the base of everything the player can own**: `DisplayName`, `Description`, `Symbol`, `Tooltip` (name over description) and a `SlotKind` saying which slot category it is offered in. There are three kinds, and each *does* something different when it is chosen:

| kind | class | choosing it means |
| --- | --- | --- |
| melee / ranged weapon | `AttackActionData` | draw it — write `UnitState.AttackAction` |
| active item | `ActiveItemData` | use it — run its action on the character, consume it |
| passive item | `PassiveItem` | wear it — put its traits on `UnitState.Traits` |
| artefact | `Artefact` | wear it for good — a passive item in a slot nothing else is offered |

**A weapon is still an `AttackActionData` and nothing else** — no wrapper SO. `ActionData<,>` derives from `Item`, which is what lets the weapon and the attack stay the same asset; an action that is not carried (the move action) keeps `SlotKind.None` and is never offered. `AttackActionData.Kind` (`WeaponKind.Melee | Ranged`) stays its own enum so a weapon asset can only be tagged melee or ranged, and `Slot` maps from it — authored rather than read off `Condition.Range`, since traits change the effective range and the slot must not change with them.

**An active item is an action, not a thing that holds one.** `ActiveItemData : ActionData<ActiveItemCondition, ActiveItemEffect>`, so it costs AP, is tested before it runs, and reports itself through the same path an attack does — which is the whole reason it is undoable without any history code. `ActiveItemAction` never varies; the authored part is the effect (`ActiveItemEffect.Apply(Unit user)` — `HealEffect`, `RestoreActionPointsEffect`). **A new active item is a new effect asset, never a new action class or a case in `ItemManager`.** Self-targeted only: activating the slot it sits in uses it on the character, and hovering that slot previews what it would cost. Aiming one at a tile or another unit needs the selection pipeline to hold an armed action, which it cannot do yet.

**An active item can also raise a stat for good instead of spending itself on the moment** — `IncreaseStatEffect`, one class for every such item, with the stat authored on the asset (`Farsight Tonic`, `Draught of Endurance`, `Heartroot Extract`). `UnitStat` names the three numbers whose base is one authored value, and each has exactly one query folding the permanent bonus into it: `Unit.SightRange`, `Unit.MaxActionPoints`, `Unit.MaxHealth` — so nobody reads `UnitState.SightRange` or the blueprint directly, and the turn's AP refresh, the fog, the AI's exploration and the reachable-tile highlight all follow a bonus without knowing items exist. The bonuses themselves are on `UnitState` (`GetBonus`/`AddBonus`, an array indexed by `UnitStat`, deep-copied by the copy constructor like `Traits`). **A further stat is an entry in `UnitStat`, a base in its query and a branch in `Unit.GrantStatBonus` — never another effect class.** That branch is the one place that knows what a raise takes to be *felt*: sight recomputes the fog, action points are also added to the turn in progress, health fills the new room. Both blob rows are built once at setup and clamp to how many blobs they have, so a moved maximum has to rebuild the row — `HealthBar.SetMaxBlobs` and `ActionsPointsBar.SetMaxBlobs` (through `ActionExecutor.RefreshActionPointsBar`, since the AP bar is the executor's), or the extra point would be spendable but never shown.

Unlike the weapon in hand, a permanent gain **is** in `GameSnapshot` (`UnitSnapshot.StatBonuses`): it cost AP and cannot be given back by choosing differently, so it is world state and can only come back by being written down. `Unit.RestoreSnapshot` puts the bonuses back *before* the health, since the bar has to have room for the recorded value.

**A passive item is a bundle of traits and no code at all.** `CombatRules` already folds `UnitState.Traits`, so wearing one is `List.Add` and taking it off is `List.Remove` (`ItemManager.Wear`) — one instance per trait, so a trait the blueprint also grants survives the removal. The passive slot holds one item, so the character wears one set. It is worn merely by being in its slot, which is why `RefreshEquipped` routes that slot through `Wear` rather than writing the array directly: a looted amulet is worn the moment it is owned, exactly as a looted bow appears in its slot.

**An artefact is that same bundle with a slot of its own** — `Artefact : PassiveItem`, differing only in its category. There are three, they lie open on the map rather than inside a box, each is worn the moment it is owned and nothing is ever offered its slot afterwards, and collecting the set wins the match (see Winning and losing). Its own `SlotKind` rather than a flag on the passive item because the category is what the slot layout, the loot table and `VictoryRules` each read to tell one apart — all three would otherwise have to learn about the flag. Everything it *does* is already there: three slots make it `HoldsOneItem` (so its key opens no picker and its ownership is capped at three), `IsWorn` puts it beside the passive in `ItemManager.Fill` (so its traits go on through `Wear`), and `Choose` has an empty case, since an artefact is in effect by sitting there and can never be given up. Being worn rather than recorded is also what makes it undoable for free: `RefreshEquipped` empties its slot when an undo takes the find out of the inventory, and `Wear` takes the traits off with it. The three are `Resources/Items/Artefacts/` — War (+4 damage), Swiftness (a step onto rough ground costs one less), Warding (+3 defence) — with their traits beside the others in `Resources/Traits/`.

There is no separate "equipped weapon" field: equipping *is* writing to `UnitState.AttackAction`, since the weapon and the attack are the same asset. The planner, the attack preview and `CombatRules` all read that one field, so they follow a swap without knowing weapons exist. It carries `[FormerlySerializedAs("baseAttackAction")]` for one session's worth of blueprint assets saved under that name; droppable once every `UnitBlueprint` has been re-saved.

**A weapon carries traits of its own** (`AttackActionData.Traits`), in effect exactly while it is drawn — a sword that crits, a bow that sees further. **Nothing equips them.** `CombatRules.TraitsAffecting` reads them off `UnitState.AttackAction` beside the unit's own and the ground's, which is what keeps them free of bookkeeping: the weapon in the other hand is not the attack, so its traits are simply never asked; a swap carries them without anything being put on or taken off; every unit gets them, not only the player's character, since an enemy's weapon comes off its blueprint and no `ItemManager` is involved; and because nothing is stored, an undo puts them back with the weapon it puts back. A passive item is copied onto `UnitState.Traits` instead because a passive is *worn* — there is no field already saying which one, the way `AttackAction` says which weapon.

They fold into movement and sight as well as combat, since all three rule sets ask that one query — a heavy weapon that slows a step is the same one field. Leave `EquipmentTrait.RequiresWeapon` at `Any` on them: a trait on a weapon is only ever asked while that weapon is the one in hand, so a requirement there is either trivially met or a contradiction. `AttackActionData.Stats` appends their summaries, which is why they read on the find card, the slot tooltip and `UnitRules`' weapon capability line at once and get no badge of their own — a weapon's traits belong to the weapon.

`Gameplay/Items/ItemManager.cs` is the player's inventory: the weapon they started with plus everything picked up since (`Pickup`), minus anything used up. One for the whole match, not one per unit — the player commands a single character, and `Begin(playerUnit)` hands it over, so the manager holds that unit and needs no spawner. **The opposing team has no `ItemManager` and cannot switch anything**; enemy units keep the weapon and traits their blueprint gives them. The starting weapon is not authored a second time: `Begin` seeds the inventory from the character's own attack, which its blueprint already names. The Initiator calls it after `SpawnEntities` and again from `Restart`, which spawns a fresh character holding none of what was equipped or looted.

**A slot is a category, not an item — but a category may have more than one slot.** **`ItemManager.SlotKinds` is the layout**: melee 0 (key 1), ranged 1, passive 2, actives 3 to 5 (keys 4 to 6) and artefacts 6 to 8 (keys 7 to 9) — three of them because there are three to find, so the empty ones are also what says how much of the set is still out there. It is a table rather than the `SlotKind` enum's own order, because that order is serialized on every item asset and in the loot settings and is not free to change; `SlotKind.None` still has to stay last, since everything counting the categories reads it as the count. The bar is told nothing about it, so `ItemManager.Setup` warns when `ItemBar.slotCount` and `ItemManager.SlotCount` disagree — otherwise a category silently loses its slot.

**How many slots a category has is how many of it can be carried, and whether it has more than one is what splits the two behaviours.** A weapon or a passive shares its one slot with everything of its kind: activating it offers *everything owned that fits there* in a column. An active item gets a slot to itself, so there is nothing to pick — activating that slot uses what is in it, and pressing 4 drinks the potion in slot 4. `HoldsOneItem` is that distinction, and `SlotsOf` is the resulting cap, which `HasRoomFor` answers pickups with. Seven short methods are the whole seam — `KindForSlot` (what a slot stands for), `SlotsOf`/`FirstSlotOf` (which slots a category has), `HoldsOneItem` (whether it is a shelf or a hand), `ItemsForSlot` (what a slot offers), `EquippedIn` (what it holds), `IsInUse` (whether that is doing anything), `Choose` (what picking it means). **A further category is a further entry in the layout and a further branch in those, and nowhere else** — the bar never learns that items exist.

**Each slot keeps what was put in it**, in `ItemManager.equippedBySlot` indexed **by slot, not by category** — choosing a bow does not empty the slot the sword is in, and drinking the potion in slot 4 does not shuffle slot 5 down into its place. `IsInUse` decides the `slot--active` mark (`ItemBar.SetSlotActive`): the drawn weapon and the worn passive are in use, a potion waiting to be drunk is not. `RefreshEquipped` (called from `ShowSlots`) keeps slots and inventory honest: the weapon in hand always fills its own slot, a slot holding something no longer owned — an undone pickup, a used-up potion — is emptied, and an empty slot takes the first owned item of its kind **no other slot is already showing** (`ItemsForSlot` filters those out, which only ever matters to a category with several slots). The passive slot is filled through `Wear` rather than written directly, so its traits follow.

`ItemBar` stays a pure view — it knows which slot is open and which entry is highlighted, nothing about items — and the manager is the only translator. The dialogue is two events and one call: the bar raises `SlotActivated(slot)`, the manager answers with `OpenPicker(slot, IReadOnlyList<ItemOption>, highlighted)`, and the bar raises `OptionChosen(slot, option)`. `ItemOption` is icon + tooltip, which is all the bar needs to draw a choice.

**A slot says what it is for before anything is in it.** `SlotLook` is what the manager pushes about a slot's *category* rather than its contents, the way `ItemOption` is what it pushes about a choice: the category's symbol, drawn faded while the slot is empty (`slot__icon--ghost`); the category's colour, worn as a strip along the bottom edge whether the slot is full or not — **not** the frame, which is where the yellow of an item in use already lives; and whether the row breaks in front of the slot. Which of the symbol and the item is showing is `ItemBar.ApplyIcon`, since the two are pushed apart and in no fixed order. Both halves of the look are authored in `SlotIconSet` (asset at `Resources/Settings/Default SlotIconSet.asset`), one entry per `SlotKind`, cells counted from the top left starting at one exactly as in `ActionIconSet` — the two share `IconSheet.Cut`. Where the row breaks is *not* authored: `ItemManager.StartsGroup` reads it off the layout table, since a category's slots are contiguous there, so the three actives read as one thing rather than as three of nine. `GroupOf` is the one exception — the two weapons stand in one run, being the weapon in hand split only by kind — and it is where a further pair that belongs together says so. A further category is therefore a further entry in the layout, a further branch in the seam methods and a further row in that asset — and the bar still never learns that categories exist.

**Finding something for the first time puts a card in the middle of the screen** (`UI/ItemPopup.cs`) — symbol, name, category, description, numbers, and which slot it landed in. Built in code on a `UIDocument` of its own like the floating damage text, created by the Initiator from the item bar's panel settings. It does not time out: a find is read rather than glimpsed, so it waits for any click or key and fades on that — polled off `Keyboard`/`Mouse` rather than through `InputHandler`, since it answers to no binding in particular, and ignored until the fade-in is done so the button that opened it cannot also close it.

**The press that puts it away is spent on it and reaches nothing else**, which takes both roads into the game because they are separate. `Runtime/Gameplay/Global/IInputBlocker.cs` is the seam: a view registered with `InputHandler.AddBlocker` is *asked* (`Blocked`) before any event is announced, so nothing has to be unset when the card goes — that covers the world raycast, the loot key, end turn, the number keys and space/escape at once, since every raise now goes through `InputHandler.Raise`. A right click is the exception in shape: it is only known to be one on release, by which time the card is gone, so `DragPan` remembers whether the *press* was blocked. Panning is deliberately left open — the game answers nothing to it. The other road is UI Toolkit's own: the item bar and the next-turn button lie under the card on the same panel and would be pressed *through* it, so while it is up the card's root picks (`PickingMode.Position`; its contents stay click-through, the card as a whole is what swallows). Both stop the moment it is dismissed, so the fade-out costs no click. `ActionHistory` polls its undo key itself and is deliberately not gated. A second view the manager talks to, not a part of the bar: it is handed an `ItemCard` of strings and a sprite, the way the bar is handed `ItemOption`s.

**Two layouts, and the layout is all they differ in.** `ItemPopup` is the wide card (symbol beside the name); `VerticalItemPopup` is the column (name and category on top, a larger symbol under them, description and numbers below, everything centered). `BuildCard` — plus `CardWidth` and `StatLine` — is the whole seam: a variant arranges the same elements and inherits when the card appears, what puts it away and what goes in it. `Initiator.verticalItemPopup` picks one, which is the only place either name is mentioned.

**An item describes itself; nothing takes it apart from outside.** `Item.Stats` is a list of short lines each kind builds from its own fields — a weapon its damage/range/cost, an active item its cost plus `ActiveItemEffect.Summary`, a passive item its traits' `Trait.Summary` — so the popup needs no switch over the three kinds and a new kind of item is still just an SO. `Item.Tooltip` — the hover label on a slot and on a picker entry — is built from the same lines, name, description, then the numbers after a blank line, so an item that grows a stat grows it on the card and on hover at once; the bar labels with a plain text element, which is why it is a string with newlines rather than a card of its own. `ActiveItemEffect.Summary` is **abstract** on purpose: an effect is the authored half of an active item, so a new one has to say what it does the moment it does it. `Trait.Summary` is virtual and falls back to the designer note, since a trait may carry no number worth printing. The only thing the item cannot say is which slot it went to, which is the manager's `SlotNameOf` — read off `equippedBySlot` rather than worked out from the category, since a category can hold several slots and only the slots know which one took this item; counted from one because that is the key the bar prints.

Only the *first* find of a thing is announced, tracked in `ItemManager.announced` — deliberately outside `GameSnapshot`, so undoing a pickup and taking the same box again is the same find rather than a second one. An undo while a card is still up hides it (`RestoreItems`), since "assigned to slot 1" stops being true.

Authored items live in `Resources/Items/` (`Active/`, `Passive/`, plus the `Effects/` and `Conditions/` an active item is assembled from); the traits passives hand out are in `Resources/Traits/` with the terrain ones. Weapons stay in `Resources/Actions/Attacks/`, since a weapon is an attack.

Interaction, and the two modalities deliberately differ: a **number key** opens its slot's picker and *repeating that key walks the column*, with space confirming (`InputHandler.ConfirmPressed`) and escape cancelling (`CancelPressed`); the **mouse** opens the picker by clicking the slot, closes it by clicking the slot again, and chooses by clicking an entry. Turning to another slot abandons the pending choice. Nothing can be put down, only swapped or used up — the picker offers no empty entry. **An active slot opens no picker at all**: it holds one item, so key and click both go straight to using it. **Hovering a slot is its preview**, the item bar's answer to hovering a tile: `ItemBar.SlotHovered` (its own event, not the tooltip's timer — the cost shows at once while the label waits out the delay) reaches `ItemManager.ShowHoverPreview`, which asks `ActionExecutor.PlanItemAction` for an active item and clears the preview for anything else, since a weapon is drawn and a passive worn for free. `ExecuteItemAction` runs that same plan, so what was shown and what is spent are the same call. Two things it has to survive: the slots changing under a resting cursor (a potion drunk out of one), which is why `ShowSlots` ends by asking again; and the cursor reaching the bar being *also* the cursor leaving the map, so the world's `SelectionNoHover` clears this preview in the same frame it is set — `ItemManager.LateUpdate` says it once more, since which of the two runs last is up to where the panel's pointer events land in the player loop.

Which weapon is in hand and which passive is worn are deliberately **not** in `GameSnapshot`: they are loadout, not world state (free to change, no AP, reported as no action), and both are re-derived from the recorded inventory by `RestoreItems` → `ShowSlots`. What the player *owns* is a different matter — picking an item up and using one both cost AP, so the inventory does travel with the snapshot; see Loot below.

### Merging

`Gameplay/Global/MergeRules.cs` is the `CombatRules`-style query for making two items into one: pure functions over a pair, no state and **no random number** — the roll belongs to whoever spends the items, so the odds can be drawn as often as the cursor moves without deciding anything. The screen that shows the chance and the manager that pays it ask the same call, so they cannot disagree.

**Left is improved and survives, right is taken apart and is spent either way.** The left slot takes a weapon and nothing else, because a weapon is the one thing whose traits are carried without being worn — `CombatRules.TraitsAffecting` reads them straight off `UnitState.AttackAction`, so a merged one needs no bookkeeping anywhere to take effect. The right takes a weapon or a passive item carrying at least one trait; `MergeRules.TraitsOf` is the one place `AttackActionData.Traits` and `PassiveItem.Traits` are bridged. An `Artefact` is turned away by the type test — it is worn for good, never given up, and the set is a win condition.

**The chance is one over the number of traits the weapon would end up with.** One formula, not a starting value and a penalty: "100% while it has none" falls out of it, since a merge leaving one trait is one over one, then a half, then a third. Duplicates are counted rather than weeded out, so passing on a trait the weapon already has both stacks it and makes the next merge harder — the same trade every merge is. On a failure the right item is gone and the left is untouched.

**`MergeRules.Combine` makes a runtime copy of the weapon, never writes the asset.** A weapon is a ScriptableObject shared by every unit whose blueprint names it and by the loot table; writing a trait into one would improve it for the enemy holding the same sword and would survive the match into the project files. The copy is `HideFlags.HideAndDontSave` like a cut icon sprite, with `FoundIn` cleared, and it is what the inventory then holds — so it travels through `GameSnapshot.Items` as an ordinary item reference, an undo puts both originals back by itself and a redo hands back the very same weapon instead of rolling again. Copies are never destroyed: a snapshot behind the cursor still refers to them.

Merging costs no AP and does not wait for the player's turn — it is loadout, like drawing a weapon. It is still **reported** (`ActionKind.Merge`), because unlike drawing a weapon it destroys something; `HistoryEntry` reads which way it went out of the two snapshots (an item in the after-list that was not in the before-list) rather than off the report, like every other outcome there. `ItemManager.DropUnownedWeapon` is the one rule for a weapon that has left the inventory, shared by the undo and the merge; a merge while the left weapon is drawn puts the copy in hand, since the weapon in hand is a reference and not a slot.

`UI/MergeScreen.cs` is the workbench: a button in the bottom-left corner (its symbol is `ActionKind.Merge` in `ActionIconSet` — merging is a kind of action, so a further entry there rather than a look decided in the view) and the panel it opens. A pure view like `ItemBar`, holding the same two things — which slot is open and which entry is highlighted — and talking the same three-step dialogue: it raises `SlotActivated(side)`, the manager answers with `OpenPicker(side, IReadOnlyList<ItemOption>, highlighted)`, it raises `OptionChosen(side, option)`. `ItemOption.Label` was added for it: the bar draws a tight row of symbols and ignores it, the merge columns have room and print the name, so a choice reads without waiting out a hover. Built in code on a `UIDocument` of its own like `ItemPopup`, sharing the HUD's panel settings — which is also what keeps a click on it out of the world, since `Raycaster` picks every document on one panel together.

While it is open it is an `IInputBlocker`, so **escape is polled off the keyboard** rather than taken from `InputHandler.CancelPressed`: blocking swallows the very key meant to take the modal away. The merge slots are re-checked against the inventory on every `ShowMerge`, because an undo, a merge or a drunk potion can take away what one of them was holding.

### Loot

`Core/Spawning/LootSpawner.cs` makes every box of the match and owns them, the way the other spawners own their tiles and units. The Initiator calls `SpawnLootboxes()` **last** in `SpawnEntities` — scattered boxes avoid tiles somebody stands on, and how many drops are worth making is how many units there are to fall, so the units have to be down first. Scatter candidates are `CanLieOn && !IsOccupied`, shuffled once and then handed out per tier by distance from the middle (see the ring below). **`LootSpawner.CanLieOn` is the whole rule for where a box may lie** — passable ground and nothing else, since a box is taken by standing on it — and it is asked in `Place`, the one door onto the board, rather than at each caller, so the scatter, a drop and a snapshot restore obey it alike. A box refused a tile is left where it was rather than put somewhere nobody could reach it: a drop simply stays pending for the next unit to fall.

What a box holds is rolled **when it is made**, not when it is opened, so a given board hands out the same thing however late the player walks over it — the same reason redo reproduces a critical hit instead of re-rolling it.

**A kind of box is a whole ScriptableObject** — `Data/LootboxType.cs`, assets in `Resources/Loot/`. There are three, and they are **tiers**: `Lootbox Tier 1` (Worn Crate), `Tier 2` (Iron-Bound Chest), `Tier 3` (Gilded Reliquary), each costing and holding a little more than the one under it. A type carries the sprite, the `PickupCost`, how many boxes of each category it accounts for, how far out on the map they lie and how many of them are dropped rather than scattered; `LootSpawnerSettings` is left with only what belongs to no kind — the shared prefab, the list of `Types` in play, the sorting order and the `Scale` every box is drawn at (which replaces the prefab's own, exactly as the type's sprite does, so the tier is still read off the silhouette rather than off the size). A further tier is a further asset and no code: not a new prefab either, since the type's `Sprite` replaces what the shared one carries.

**The loot table is authored from the item's side, not the box's.** `Item.FoundIn` names the `LootboxType` an item turns up in, so an item is put into play by the same asset that defines it and there is no second list to keep in step; an item naming none is never found, which is what the weapon the character starts with wants. A box therefore lists no contents at all, and `LootSpawner.CollectItems` reads the table off `Resources.LoadAll<Item>` and files each item under its type and its own `SlotKind`. Loading rather than listing is the point: **nothing may hold a second copy of which items are in play**, or the two drift apart the first time an item is added and only half wired up. It re-reads on every spawn, so an item moved to another tier in the inspector is in the right one from the next match.

**How much of each category appears is authored, not left to chance.** Each type carries one count per `SlotKind` — `MeleeWeaponCount`, `RangedWeaponCount`, `ActiveItemCount`, `PassiveItemCount` — and `LootboxCount` is their sum rather than a field of its own, so the total and the parts can never disagree: a box exists because something was asked to be in it. The spawner keeps **one bag per type and category**, each a shuffled copy of the matching pool refilled only once empty, so a handful of authored items don't repeat, a category with many items doesn't crowd out one with few, and two tiers offering the same item don't deal from one pile. A count for a category no item assigned itself to warns and places no box — and the warning points at the item side, since that is where the assignment lives.

**`LootboxType.DroppedCount` splits a kind between the two ways one turns up.** That many of its boxes wait for an opposing unit to fall; the rest are put down over the map when it is generated. Which ones wait is drawn from that kind's own boxes at random, so a drop is the tier's authored mix rather than whichever category was listed first — and every tier can do both, which is why this is a count and not a placement enum. It is capped by how many enemies there are to fall, and a scattered box with no tile left is not made at all rather than left pending, since a pending box no fall will ever place could never be collected.

**Where the scattered ones lie is authored on the kind as well, and the tier is the distance.** `MinDistanceFromCenter` / `MaxDistanceFromCenter` are the ring a kind's boxes are put in, as a fraction of the way from `TileSpawnerSettings.GridCenter` — the very middle the player spawns around — to the furthest tile of the grid: tier 1 at 0–0.3, tier 2 at 0.3–0.65, tier 3 at 0.65–1, so a better find is a longer walk out of the middle and the artefacts (0–1) lie anywhere. A fraction rather than a count of tiles, so resizing the map does not re-author every tier, and Euclidean like the player's spawn circle, so it reads as a ring rather than as Manhattan's diamond. `TileSpawner.DistanceFromCenter(Tile)` is the query, since anything spatial belongs to the spawner that owns the tiles, and `TileSpawnerSettings.GridRadius` is what it divides by. `LootboxType.DistanceOutsideRing` is the miss distance and is **deliberately the same shape as `TileSpawnerSettings.DistanceOutsideZone`**: candidates are *ordered* by it rather than filtered, so a ring walled off by mountains or already emptied by the tier before it spills over its border instead of losing its boxes. That is also why the kinds are placed one whole kind at a time and what one takes is gone for the next (`LootSpawner.OrderByRing`); the single up-front shuffle survives as the stable sort's tiebreak, so a tier lands somewhere else along its ring each match while staying at its distance. Scattered boxes only — a drop lands wherever its unit fell, which is no tier's business.

A box is **not clickable and does not occupy its tile**: it is taken by standing on it and pressing `E` (`InputHandler.InteractPressed`) or right-clicking, so it needs no collider and must not block the way to itself. `Tile.Lootbox` is where a box is parked — one step to find it, and it follows the fog the ground is already tinted with (`Tile.RefreshLootbox`; visible on *remembered* ground too, unlike an enemy, because a box does not move).

Taking one is a **turn action**: it costs what `LootSpawner.PickupCostOf` asks — the `PickupCost` of its own kind, so a heavier kind can simply ask for more, and nothing at all while auto-collect is on (see below), it only works on the character's own turn and only while it can afford it, and it reports `ActionKind.Pickup` so the history can undo it. The three conditions (a box here, points to spend, room for what is in it) are checked inline in `LootSpawner.TryPickup` rather than through an `ActionData` SO — the pickup has no per-unit authoring and no target, so a `PickupCondition`/`PickupEffect` pair would carry nothing but the cost, which lives on the type instead. Give it the full action pipeline the moment it grows a real condition.

**`GameRules.AutoCollectLootboxes` (off by default) makes walking over a box enough**, and then it costs nothing and announces nothing. Every tile of a move arrives at `LootSpawner.HandleUnitEnteredTile`, so boxes *on the way* are taken rather than only the one the path ends on. It reports no `ActionKind.Pickup` on purpose: it happens **inside** a move, one step of one, so the move's own report is what records it — that report's after-snapshot has the box gone and the item owned, and one undo takes back the step and the find together. A report of its own would capture a move half walked with its points not yet paid, since `ActionExecutor.ExecutePlannedActions` charges the whole plan at the end. The pressed pickup stays wired either way and is then **free as well** (`PickupCostOf` returns 0 while the switch is on): with a step enough to have a box, pressing for the one already underfoot must not be the expensive way of doing the same thing — and that is no corner case, since a box holding something there was no room for is left lying and no further arrival will pick it up, so pressing is the only way back to it once a slot has been freed. Both paths share `LootSpawner.TryTake`, which is the whole of taking a box — they differ in what they cost and what they announce, nothing else.

The seam is `UnitSpawner.UnitEnteredTile`, raised from `Unit.PlaceOnTile` after the fog recompute: the spawner that owns the units announces an arrival, so nothing that cares what lies on the ground has to be threaded into `Unit.Init`. `Unit.RestoreSnapshot` writes the position directly and never passes through it — putting a unit back is not an arrival, or an undo would collect the box it just gave back. Only the player's character collects: nobody else has an inventory.

**A fallen enemy leaves a box behind**, and it is a lootbox in the full sense — its own type asset, its own contents, its own cost, taken the same two ways. `UnitSpawner.UnitRemoved` is the seam, the exact mirror of `UnitEnteredTile`: raised from `Unit.Remove` once the unit is off the board and its tile is free, so what a fall is worth is no more the unit's business than what it is standing on. A snapshot restore removes units without passing through it, or an undo would drop the spoils a second time; `Unit.Remove` also returns early when `!IsAlive`, so a unit can only fall once.

**A drop is not a box coming into being — it is a box that was always there being put down.** Every drop is made and filled with the scattered ones at `SpawnLootboxes`, then held in `LootboxState.Pending`, which is what makes it undoable with no history code: its contents were rolled once, so redo hands back the very item undo took away, and it is in the first snapshot like everything else. `LootSpawner.dropOrder` is shuffled once at spawn and never touched again; the *next* drop is the first entry still pending, so nothing about the drops has to be recorded — undo puts a box back to pending and it is next again. The drops of all three tiers share that one queue, so what a kill leaves behind is any tier. Only opposing units leave one (the player's fall ends the match rather than furnishing it), and a tile already holding a box keeps the one it has, leaving the drop pending for the next unit to fall.

**Three states, not a bool** (`LootboxState`): `Pending`, `InPlay`, `Taken`. A drop is neither on the board nor taken off it, and that distinction is what lets `VictoryRules` wait for spoils nobody has died for yet — and stop waiting once no opponent is left to leave them. `Lootbox.SetState(state, tile)` moves both together on purpose, since a box in play is exactly a box some tile is showing; `LootSpawner.Place` is the one door to it, because where a box stands and whether it is on the board are the same question. `LootboxSnapshot` therefore records the tile as well as the state: a scattered box never moves, but a dropped one lies wherever a unit happened to fall.

**A box holding something that cannot be taken is left where it lies**, unopened and costing nothing, so it can be come back for once a slot is free or the copy already carried has been used up — and since an unopened box looks exactly like one that was never walked over, the character says why: `Unit.ShowNotice` puts a `FloatingText` over its head, the same channel the damage numbers use (`FloatingTextSettings.NoticeColor` / `NoticeFontSize`, smaller than a number because it is a sentence).

**`ItemManager.CanTake(item, out reason)` is the single rule for that, and it must stay single.** It turns away two things — an asset already owned that its category may not stack, and a full category (`HoldsOneItem`, so today only actives with their three slots; copies count, so three of the same draught fill it as surely as three different ones) — and it hands back the sentence to show. It exists as one query because it once was two: a cap asked by the loot before opening a box, and a duplicate check enforced inside `Pickup`. A box holding a duplicate passed the first and failed the second, and so was opened and emptied for nothing. `Pickup` asks it again rather than trusting the caller, but both now ask the same thing. **Anything else that hands the player an item asks it too** — never `items.Add`.

Duplicates matter more than they look: the loot deals from a bag it refills once empty, so `ActiveItemCount: 30` against five authored active items puts each of them in about six boxes. Most boxes hold something already carried.

**A kind of find need not be a box.** `LootboxType.ShowsContent` draws what lies on the tile with the *item's* symbol instead of the kind's sprite, which is what artefacts are: the find lies open and is read from across the map rather than opened for a surprise. `Lootbox.SpriteFor` is the whole of it, and it falls back to the kind's sprite for an item with no symbol authored yet, so nothing goes invisible while art is still being drawn. Everything else about a box it keeps — the fog tint, the tile it is parked on, both ways of taking it, the snapshot that undoes it. The `Artefact` type in `Resources/Loot/` asks for three of them, drops none (a fallen enemy leaves tiers, not artefacts) and therefore scatters all three; because the bag is dealt without replacement, each artefact is placed exactly once.

Sprites live in `Resources/Visuals/Loot/`, one per tier, drawn **straight on** rather than in the 3/4 view the first box was in — a box reads the same wherever on the grid it lies, and nothing about it has to be redrawn if the camera angle is ever touched. They are a ladder and are meant to be read as one: bare boards, then wood bound in iron, then wood bound in gold with a stone in the lid and sparkles around it. Each is wider and taller than the one below, so **the tier is legible from the silhouette alone** — before the detail, and through the fog tint, which is why the top tier gets sparkles rather than merely more gold.

### Carrying two of the same thing

`GameRules.StackDuplicateActiveItems` (on by default) lets the same active item be carried more than once — three Healing Draughts fill the three active slots. **Only a category that carries one item per slot can stack, switch or no switch** (`CanStack` = `HoldsOneItem` && the switch): everywhere else the whole category shares a single slot, so a second copy would have nowhere of its own to be and would do nothing while it sat there — a second identical sword is not a sword to swing, a second amulet grants no more traits. A copy is only worth owning where owning it means a use in hand. With the switch off, a box holding anything already carried is left where it lies with "Already carried".

**The consequence for the slots is that they hold *copies*, not identities, so `RefreshEquipped` counts instead of comparing** — this is the part that breaks if it is written back the obvious way. A slot is backed by the inventory only while the copies shown up to it are copies owned (`CopiesShownUpTo(slot) > CountOwnedOf(item)` empties it, which covers an undone pickup, a used-up potion *and* the second of two slots once one of a pair is drunk), and an empty slot takes the first owned item of its kind the slots do not already show every copy of (`FirstUnshown`). `items.Contains` and a plain "is it held elsewhere" test both give the wrong answer once two slots hold one asset — two such slots each see the other holding "it" and neither will fill. `ItemsForSlot` stays a plain category filter because only the non-stacking categories are ever picked from.

`Use` removes *one copy* (`items.IndexOf`), and which slot goes empty over it is `RefreshEquipped`'s business, not the caller's — the copies are the same asset, so there is no question of which one was drunk. `announced` is unchanged and still keyed by asset: a second copy is not a new find and shows no card.

Because it costs AP it is world state, so `GameSnapshot` records **boxes and inventory together** — undoing one without the other would hand out the same item twice. `LootSpawner.TakeLootbox` therefore *hides* a box rather than destroying it (`Lootbox.IsInPlay`), exactly as `UnitSpawner.RemoveUnit` keeps a fallen unit. Using an active item shortens that same inventory, which is why `ItemManager.Use` takes the item out **before** running the action: the executor reports itself when it is done and the after-snapshot is captured at that moment, so an item still in the list there would be handed back twice. What is in hand or worn is still not recorded — `RestoreItems` re-derives both.

**Right-click is now a release, not a press.** The same button drags the camera, so `InputHandler.DragPan` raises `RightClicked` only when the button comes up without having travelled more than `ClickTravelThreshold` pixels. There is no `rightClickAction` any more.

### Grid and spawning

`Core/Spawning/TileSpawner.cs` owns all tiles and is the query surface for anything spatial — `GetPath`, `GetAttackApproachPath`, `GetMoveableTiles`, `GetThreatenedTiles`, `GetVisibleTiles`, `GetDistanceBetweenTiles`. It delegates to `Pathfinder` so impassable terrain, occupancy and difficult-terrain costs are honoured; don't reimplement distance or reachability against raw positions. Grid distance is **Manhattan**; fog sight is **Euclidean**. `GetVisibleTiles(Unit, Tile)` is the sight query — the circle `GetTilesInSightRange` draws, minus what `SightRules.BlocksSight` hides, tested by walking the line tile by tile (neither end is asked, so a hill is seen from below and only what stands behind it is not). Tiles are also kept in a position→tile dictionary, since sight walks a line per tile and a `List.Find` per step of it adds up over a fog pass.

`UnitSpawner` spawns from `UnitBlueprint` SOs. `UnitBlueprint.DefaultState` returns a **fresh copy** via the `UnitState(UnitState other)` constructor (including a new `Traits` list) so runtime state never aliases the asset — preserve that when extending `UnitState`.

`UnitState` exposes `Health`/`ActionPoints` as properties that fire callbacks and raise `OnNoActionsLeft`; `ActionPoints` throws on negative values.

**The two spawn zones are measured from opposite ends of the map, which is what makes the opponents encircle the player.** `TileSpawnerSettings.GetSpawnZonePositions(team)` puts the player within `PlayerSpawnRadius` of `GridCenter` — Euclidean, like fog sight, so it reads as a circle rather than Manhattan's diamond — and the opponents in the `OpponentSpawnZoneSize`-deep band along the rim, counted inwards from the nearest edge (`DepthFromRim`), so a size of 1 is the outermost tiles and nothing else. Neither zone is told where the other landed, and neither needs to be.

It returns **every** grid position, the zone's shuffled and the rest ordered by how far outside they fall, and `UnitSpawner.PlaceUnit` walks that list until a tile takes the unit: a zone can be walled off by mountains or filled by the units already placed in it, so it has to spill over its border — re-rolling inside it would spin forever.

`UnitSpawner.RemoveUnit` does **not** destroy — it moves the unit to `removedUnits` and calls `Unit.SetInPlay(false)`, which hides it via `SetRevealed` (not `SetActive`, which would make the UIDocument rebuild its tree and wipe the health/AP blobs). `RestoreUnit` reverses it. `Unit.IsAlive` is the authoritative "in play" test; only `ClearUnits` (respawn) actually destroys.

### Undo/redo

`Gameplay/History/` records every action since the match started and can put the game back at any point in that record.

- `ActionReporter` is a static announcement channel; `ActionExecutor`, `LootSpawner` (pickups) and `GameStateManager` (via `TurnStarted`) are the things that report today.
- `ActionHistory` (created at runtime by the Initiator, wired by `Setup`) holds a `List<HistoryEntry>`, each with the `GameSnapshot` before and after the action. A `cursor` marks the position: the index of the next action to be (re)done. Recording while the cursor is behind the end truncates the redo branch.
- `GameSnapshot` is a **whole-world** capture (per-unit placement/vitals/alive, turn state, explored map) restored wholesale — not an inverse action. That is why redo reproduces a critical hit exactly instead of re-rolling it, and why a new mechanic is undoable as soon as it reports. Restore order is load-bearing: turn first (so `TurnReset` rebuilds fog owner/facing/selection), then units over it, then one fog pass.
- `GameStateManager.RestoreTurn` fires `TurnReset` but deliberately **never `TurnStarted`** — the turn's actor already played it. Restoring a snapshot calls `AiController.CancelTurn()`; `ResumeTurn()` hands the turn back.
- Editor: **Tools ▸ Action History**. Page Up / Page Down step back and forward — plain keys because the editor claims Ctrl/Cmd+Z for its own undo. Bound twice: in `ActionHistory.Update` (fires only while the **Game view** has focus) and as a `[Shortcut]` on the window (fires while the window has focus, rebindable under Edit ▸ Shortcuts).

### Winning and losing

`Gameplay/Global/VictoryRules.cs` is the `CombatRules`-style query for the other end of the match: `Evaluate` reads the board and returns a `MatchResult` (`MatchOutcome` plus the sentence the screen shows). Five conditions, each switchable in `GameRules` — `WinByDefeatingAllEnemies`, `WinByExploringMap`, `WinByCollectingAllArtefacts`, `WinByCollectingAllLoot`, `LoseWhenCharacterFalls`; with all of them off a match simply never ends. **Defeat is asked first**, so a character that falls to the retaliation of the last enemy it struck down has lost rather than won by a hair. Exploration counts **passable tiles only**: the inside of a mountain range may never come within sight of anywhere the character can stand, and a win nobody can reach is worse than none.

**Each condition asks the board, never a tally.** Both team checks say "had units and none are left", and the loot check "had boxes and every one is taken" — a removed unit and a taken box are only hidden, which is what tells *wiped out* / *all collected* apart from *not spawned yet*. **Taken, rather than merely off the board**: a box waiting for an enemy to fall is on no tile yet but is not collected either, so it holds the win open — but only while an opponent is left standing to leave it behind, or a drop nobody could ever reach would hold it open forever. The loot condition deliberately does **not** ask the inventory: a box holding something already carried is left where it lies, so what the player owns says nothing about what is still out there — the win simply waits until it has been come back for with a slot free. **The artefacts are that same question asked of fewer boxes**, not a condition of its own: `IsAllLootCollected` takes an optional `SlotKind`, so the two share their whole answer — including what counts as taken and what a board with none of them means. It is asked *before* the general loot check, since an artefact is loot as well and collecting the set is the more particular thing to have done, so it should be the sentence the screen shows.

**The outcome is never stored — that is what makes it undoable for free.** Every condition is a function of state `GameSnapshot` already records (who is alive, what is explored, which boxes are still out), so putting the board back puts the verdict back with it, exactly as the weapon in hand is re-derived rather than recorded. Nothing in `Gameplay/History/` knows victory exists.

`MatchOutcomeWatcher` (created at runtime by the Initiator on its own object, like the attack preview) is what asks and what announces. **Its two channels are timed differently, and that is load-bearing.** `ActionReporter.ActionExecuted` is answered *on the spot*: an action announces itself once the board is whole again, and a turn behind the fog is paced by nothing and plays itself out inside a single frame, so a verdict held back would arrive after the actions it was meant to stop. `GameStateManager.GameStateChanged` sets a flag read in `LateUpdate` instead: a snapshot restore raises it several times while the board is half taken apart, and waiting out the frame asks once, of a board that is whole either way. A restore's *last* act is `SetActionsLeft`, which is how undo and redo are noticed without the history saying anything.

**A decided match stops moving.** Three subscribers, one each for the three ways play continues: `AiController` (drops the turn it is playing and starts no further one — taking the verdict back only lifts the block, the turn is handed back by asking `ResumeTurn`, the way a restored one is), `NextTurnButton` (the one place that owns ending a turn, so the button and **Q** stop together), and `Selector.HandleClick` (the head of the selection pipeline, so one refusal covers moving, attacking and everything else a click leads to — hovering is left alone, a preview changes nothing). Everything unfreezes by itself when an undo reopens the match.

`UI/GameOverScreen.cs` is the card on a dimmed screen, built in code on a `UIDocument` of its own like `ItemPopup`, but click-through where the find card swallows — nothing dismisses a verdict, so it blocks nothing, and the undo key reaches `ActionHistory` exactly as it does during play, which is the whole point. Nothing dismisses it: it goes up when the watcher announces a verdict and comes down when the verdict does. The hint line names `ActionHistory.UndoKey` rather than spelling a key out, so a rebind carries.

### AI

`Gameplay/AI/AiController.cs` drives a team on `TurnStarted`: per unit, attack the closest reachable enemy, else advance on the closest visible enemy, else move to uncover unexplored map; hands back via `ToggleCurrentTeam()`. Capped by `maxActionsPerUnit`. `aiEnabled` is live-toggleable (`ToggleEnabled` context menu) to play the AI team manually; `Drives(team)` answers whether the AI — rather than the player — is playing a given turn, which is what lets the fog hide that turn without hiding a turn the player took over.

**`actionDelay` is spent on the audience, not on the AI**: `ActUnit` waits **after** an action, and only while `FogOfWar.IsShown(unit)`. After, not before, because that is when it is knowable — a unit stepping out of the fog is invisible right up to the moment it arrives, and the turn's closing action is the one nothing follows, so both would go unpaced by a check taken beforehand. `RunTurn` pays the one beat that has no action ahead of it (the turn's first) when any of its units is already in sight. With enemy turns shown the viewing team *is* the acting team, so every AI unit qualifies and pacing is unchanged; a turn entirely behind the fog never waits and resolves as fast as it computes. `RunTurn` therefore opens with a bare `yield return null`: `StartCoroutine` runs a coroutine up to its first yield synchronously, and an unpaced turn would otherwise play out *inside* the `TurnStarted` dispatch that started it — the closing `ToggleCurrentTeam` would compare against a `previousState` that raise has not written back yet, see no team change and skip the player's own `TurnReset`.

### Fog of war

`Gameplay/Fog/FogOfWar.cs` recomputes on `TurnReset` and after every unit move, and pushes the result onto tiles (lit / remembered / hidden) and units (shown / hidden). It collects answers rather than working them out: how far a unit sees and what the ground hides from it is `SightRules`, asked through `TileSpawner.GetVisibleTiles`, so the fog, the AI's exploration scoring and the unit card cannot disagree about what a hill is worth. Sight is Euclidean while grid distance is Manhattan.

**Two teams, deliberately split.** The **active** team is whose sight grows the explored map and answers `IsVisible` — the AI reasons with that, so it must always follow the turn. The **`ViewingTeam`** is only whose eyes the screen is drawn through. They are the same team except when `GameRules.ShowEnemyTurns` is off and `AiController.Drives(activeTeam)`: the view then stays on `Team.Player`, so the AI's moves surface only where the player's own units can see them, while the AI keeps seeing with its own eyes. Anything new that renders visibility takes the viewing team; anything that *reasons* about it takes the active team. `IsShown(Unit)` is the viewing-team half in unit form — the same test `ApplyUnitVisibility` pushes onto every unit, which is why the AI can ask it whether an action is worth pacing.

**`GameRules.HideUnexploredTerrain` (on) hides *what* the ground is, not just what stands on it**: a tile nobody has scouted is drawn as flat terrain — the flat profile's own sprite and colour, and unraised, since a mountain gives itself away by its silhouette as surely as by its rock. Remembered ground keeps its real look, like the lootbox on it: terrain does not move, so what was seen there is still true. It is a **look only** — `Tile.ApplyTerrain` still stores the real `IsPassable`, `ExtraMoveCost`, `Elevation`, `HeightOffset` and traits, so pathfinding, sight and combat never see the disguise and whatever stands on a tile is still placed on top of the true terrain (a tile is only disguised while it is hidden, and everything on a hidden tile is hidden with it). `Tile.ApplyLook` is the one place either look is drawn, so the sprite, the tint and the height can never disagree; the tile is raised by the *difference* from the height it currently stands at rather than from a remembered ground position.

Both `GameRules` and `aiEnabled` are live references but the fog is pushed rather than polled, so `Update` recomputes when `ViewingTeam` or `HideUnexploredTerrain` drifts from what was last drawn — that is the only reason the class has an `Update`.

### UI

UI Toolkit throughout (`.uss` at `Assets/`, world-space panels for health bars / AP bars / floating text). `ActionsPointsBar` shows committed vs. previewed cost as separate blob counts, which is how move previews read as "this will cost you N" - and a previewed point is drawn as the icon of the action about to spend it. The row is spent from the right, so the icons are handed over reversed: the plan's first step sits on the far right where the next point goes, and the strike it walks up to ends up on the left beside the points that survive it — reading right to left is reading the plan in order, and a blob vanishing is the step it stood for being taken. It is handed `Sprite`s rather than actions, the way `ItemBar` is handed `ItemOption`s; the translation is `ActionExecutor.PreviewIcons`, off `IUnitAction.Kind`. Which cell of which sheet stands for which `ActionKind` is authored in `ActionIconSet` (asset at `Resources/Settings/Default ActionIconSet.asset`, cells counted from the top left starting at one), so **a further kind is a further entry there** and a kind with no entry keeps the plain faded blob. `IconSheet.Cut` is where that convention is written down, shared with `SlotIconSet` (see Items).

`NextTurnButton` owns ending the turn for the player: it subscribes both its click and `InputHandler.EndTurnPressed` (**Q**) to `ToggleCurrentTeam`, so the shortcut ends the turn on exactly the same terms as the button. A keyboard shortcut lives on the element that owns the action, the way `ItemBar` owns the number keys.

## Editor tooling

`Assets/Scripts/Editor/History/ActionHistoryWindow.cs` — the action list (Tools ▸ Action History). Owns no state: it finds the running `ActionHistory` with `FindFirstObjectByType` (like `InGameSelectionMirror`) and polls its `Version`, which survives domain reloads and play-mode changes without re-subscribing.

`Assets/Scripts/Editor/WatchDashboard/` — a persistent watch window. `WatchBoard` is a ScriptableObject (survives recompiles and play-mode toggles) holding `(target, serializedPropertyPath, label)` entries picked from inspector context menus.

**Odin caveat, important for any editor work here:** `InspectorConfig.asset` sets `defaultEditorBehaviour: 11`, so Odin draws *every* user MonoBehaviour/ScriptableObject and **suppresses Unity's `contextualPropertyMenu` and `CONTEXT/Component` hooks**. Only built-in types (e.g. Transform) keep Unity's inspector — the telltale symptom is "the context menu only works on Transform". Two approaches that do work, both used by WatchDashboard:

1. **Inside Odin inspectors** — a generic `OdinValueDrawer<T>, IDefinesGenericMenuItems` at `[DrawerPriority(DrawerPriorityLevel.WrapperPriority)]` whose `DrawPropertyLayout` just calls `CallNextDrawer(label)` (draws nothing), implementing `PopulateGenericMenu`. Generic over `T`, so it applies everywhere. See `WatchOdinContextMenu.cs`.
2. **Menus Odin never touches** — `[MenuItem("GameObject/…")]` and `[MenuItem("Assets/…")]`, building a `GenericMenu` and calling `ShowAsContext()`. The GameObject variant fires once per selected object, so debounce on `EditorApplication.timeSinceStartup`. See `WatchMenu.cs`.

## ImToolkit package

`Packages/com.duxaeternus.imtoolkit` — a local immediate-mode debug UI layer over UI Toolkit, replacing `OnGUI`/`GUILayout` overlays. Call `IM.Label` / `IM.Button` / `IM.Slider` from any `Update()`; no UXML, USS, PanelSettings or scene setup. Layout scopes (`IM.Window`, `IM.Row`, `IM.Box`, `IM.Scroll`) are `using` blocks. Each call advances a cursor through a retained node list, reconciled at end of frame via a player-loop hook.

Two behaviours to know: **clicks report one frame after the press**, and widgets are **keyed by title/label** — pass the optional `id:` argument when label text is dynamic or call order changes between frames, or state will attach to the wrong widget. See the package README for the full API and the IMGUI migration table.

## Conventions

- Namespaces do **not** always mirror folders — action types live in `Actions` while their infrastructure is in `Runtime.Gameplay.Actions`, and both appear in the same files. Follow the file you are editing.
- Systems are wired by explicit `Setup(...)` injection, not `FindObjectOfType` or singletons-by-static.
- State snapshots are cloned into `ChangeEvent<T>`; observers get values, not live references.
- Prefer `[Tooltip]` on designer-facing serialized fields — the existing traits and AI settings are documented that way.
- `gitattributes` (no leading dot, at repo root) configures LFS and `unityyamlmerge` for Unity YAML.
- answer in english unless the question is in german
