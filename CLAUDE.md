# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Turn-based isometric tactics prototype (part of **DuxAeternus**). Unity **6000.3.11f1**, URP, new Input System, Odin Inspector, Singularity Hot Reload. Repo root holds the Unity project in `IsometricTest/`; the single scene is `IsometricTest/Assets/Scenes/SampleScene.unity`.

## Assemblies and compiling

There are **no asmdefs under `Assets/`** — everything compiles into the default `Assembly-CSharp` (runtime) and `Assembly-CSharp-Editor` (anything under an `Editor/` folder). The only asmdefs are in `Packages/com.duxaeternus.imtoolkit` and the Odin math module.

`Core.csproj`, `Data.csproj`, and `Gameplay.csproj` are **stale leftovers** with no matching asmdefs — ignore them. `Assembly-CSharp.csproj` is authoritative.

### Compile-check without launching Unity

Verified working. Run from `IsometricTest/` (the folder holding the `.csproj` files):

```bash
grep -oE "<HintPath>[^<]+</HintPath>" Assembly-CSharp.csproj | sed -E 's#</?HintPath>##g' | awk '{print "-r:\"" $0 "\""}' > /tmp/refs.rsp && echo '-r:"Library/ScriptAssemblies/DuxAeternus.ImToolkit.dll"' >> /tmp/refs.rsp && grep -oE '<Compile Include="[^"]+"' Assembly-CSharp.csproj | sed -E 's#<Compile Include="##; s#"$##' | sed 's#\\#/#g' | sed 's/^/"/; s/$/"/' > /tmp/srcs.rsp && csc -nologo -nostdlib+ -noconfig -target:library -langversion:latest -out:/tmp/check.dll @/tmp/refs.rsp @/tmp/srcs.rsp
```

Use `Assembly-CSharp-Editor.csproj` for editor scripts. Notes: the `.csproj` is regenerated by Unity and will not list brand-new files, so append them to the source list explicitly; runtime scripts are interdependent, so compile the full list in one go. `csc` lives in `/Library/Frameworks/Mono.framework`; **zsh does not word-split unquoted vars**, so quote source paths individually. A clean compile (DLL produced, warnings only) means Unity will accept it. The `CS0649 never assigned` warnings on `[SerializeField]` fields are expected — Unity assigns those.

Editor install: `/Applications/Unity/Hub/Editor/6000.3.11f1`.

## Architecture

### Composition root

`Runtime/Core/Initiator.cs` is a **manual DI root** — no framework. Its `Awake()` runs `SetupReferences()` → `SpawnEntities()` → `SetupUI()` → `StartGame()`, wiring every system through explicit `Setup(...)` calls in a deliberate order. Systems are `MonoBehaviour` singletons on a Systems prefab, referenced via `[SerializeField]`. When adding a system, wire it here — **order matters**, since `Setup` is also where event subscriptions happen.

`Restart()` (context menu) deliberately skips `SetupReferences`/`SetupUI` so persistent singletons don't re-subscribe. Anything created at runtime instead of in the scene (`AttackPreview`, floating text) is built in `SetupReferences`.

### Turn state

`Core/State/GameStateManager.cs` owns a tiny `State` (active `Team`, `UnitsHaveActionsLeft`) and emits `ChangeEvent<T>` (previous + new snapshot, both cloned). Three events, and the split is load-bearing:

- **`TurnReset`** — phase 1, fires only on an actual team change. Per-turn world prep: AP refresh, fog/direction recompute, selection clear. Anything the turn's actor depends on subscribes here.
- **`TurnStarted`** — phase 2, immediately after; the turn is live and the AI may act.
- **`GameStateChanged`** — every change including mid-turn (e.g. `SetActionsLeft`), for observers mirroring state regardless of turn boundaries.

`Core/State/Direction.cs` is **static mutable state** rebound on every `TurnReset` — `Forward` means the active team's forward. Reading it outside the active turn is meaningless.

### Selection → action pipeline

This is the main input path, and it is data-driven rather than imperative:

```
InputHandler → Raycaster → Clickable (IClickable: Unit | Tile)
   → Selector  … folds hover/click/selection into a single SelectionStatus enum
   → ActionAssigner  … switch on SelectionStatus
   → ActionExecutor  … plan / test / execute
```

`Selection` (in `Selector.cs`) recomputes `Status` in `UpdateStatus()` on **every property setter** via a C# pattern-match over the `(selectedUnit, clickedUnit, hoveredUnit, hoveredTile)` tuple. Click fields are set, an event fires, and they are immediately nulled — clicks are one-shot pulses, hovers are sticky. To add an interaction, add a `SelectionStatus` case rather than special-casing elsewhere.

### Actions: plan then execute

Actions are ScriptableObject-authored and instantiated per use:

- `ActionData<UCondition, TEffect>` (SO, e.g. `AttackActionData`) holds a `Condition` SO (cost, range) + `Effect` SO, and `CreateAction(context)` returns a runtime `UnitAction<UCondition, TEffect>` implementing `IUnitAction { Cost, TestConditions(), ExecuteEffects() }`.
- `ActionExecutor` (one per unit) builds a `List<IUnitAction>` plan — a move is one action *per tile step*, so per-step terrain cost is respected — then `TestConditionsForPlannedActions()` returns the index of the first failing step, which drives the path highlighting (the reachable prefix renders differently from the unreachable tail).
- Hover plans and previews; click re-plans and executes. `PlanAttackAction` uses `GetAttackApproachPath` so ranged units stop as soon as the target is in effective range instead of walking adjacent.

Callers can hold a unit past its death, so plan methods **guard `unit` and `TargetUnit` with `IsAlive`** (plus a null check) before touching plain-C# state. Keep that guard on new action paths. Dead units are *hidden, not destroyed* — see Undo/redo below — so a plain null check is not enough.

Every executed action announces itself through `ActionReporter.Report(...)` at the end of the `Execute*` method. New execute paths should do the same, or they will not be undoable.

### Traits: the extensibility seam

`Gameplay/Traits/` — `Trait : ScriptableObject` with three no-op virtuals: `ModifyOutgoingDamage`, `ModifyIncomingDamage`, `ModifyAttackRange`. Split into `UnitTrait` (travels with the unit, listed on `UnitState.Traits`) and `TerrainTrait` (attached to terrain, applies to whoever stands there) purely so inspector lists stay type-correct.

`Gameplay/Global/CombatRules.cs` is the single place these fold together — pure math, no side effects, shared by the combat resolver, `AttackAction.TestConditions`, the planner and the attack preview so they always agree. Traits see an immutable `CombatContext` (a strike; retaliation is its own strike with roles swapped and `IsRetaliation` set) or `RangeContext`.

**Route every rule number through a `CombatRules`-style query function.** A new mechanic should be a new SO asset plus at most one new trait/effect class — never a switch case in `ActionAssigner` or a new per-type `Plan*`/`Execute*` pair on `ActionExecutor`.

`CombatRunner.ResolveCombat` applies damage, resolves retaliation (only if the defender's *effective* range reaches back), then removes the dead.

### Grid and spawning

`Core/Spawning/TileSpawner.cs` owns all tiles and is the query surface for anything spatial — `GetPath`, `GetPathWithinRange`, `GetAttackApproachPath`, `GetMoveableTiles`, `GetTilesInSightRange`, `GetDistanceBetweenTiles`. It delegates to `Pathfinder` so impassable terrain, occupancy and difficult-terrain costs are honoured; don't reimplement distance or reachability against raw positions. Grid distance is **Manhattan**; fog sight is **Euclidean**.

`UnitSpawner` spawns from `UnitBlueprint` SOs. `UnitBlueprint.DefaultState` returns a **fresh copy** via the `UnitState(UnitState other)` constructor (including a new `Traits` list) so runtime state never aliases the asset — preserve that when extending `UnitState`.

`UnitState` exposes `Health`/`ActionPoints` as properties that fire callbacks and raise `OnNoActionsLeft`; `ActionPoints` throws on negative values.

`UnitSpawner.RemoveUnit` does **not** destroy — it moves the unit to `removedUnits` and calls `Unit.SetInPlay(false)`, which hides it via `SetRevealed` (not `SetActive`, which would make the UIDocument rebuild its tree and wipe the health/AP blobs). `RestoreUnit` reverses it. `Unit.IsAlive` is the authoritative "in play" test; only `ClearUnits` (respawn) actually destroys.

### Undo/redo

`Gameplay/History/` records every action since the match started and can put the game back at any point in that record.

- `ActionReporter` is a static announcement channel; `ActionExecutor` and `GameStateManager` (via `TurnStarted`) are the only things that report today.
- `ActionHistory` (created at runtime by the Initiator, wired by `Setup`) holds a `List<HistoryEntry>`, each with the `GameSnapshot` before and after the action. A `cursor` marks the position: the index of the next action to be (re)done. Recording while the cursor is behind the end truncates the redo branch.
- `GameSnapshot` is a **whole-world** capture (per-unit placement/vitals/alive, turn state, explored map) restored wholesale — not an inverse action. That is why redo reproduces a critical hit exactly instead of re-rolling it, and why a new mechanic is undoable as soon as it reports. Restore order is load-bearing: turn first (so `TurnReset` rebuilds fog owner/facing/selection), then units over it, then one fog pass.
- `GameStateManager.RestoreTurn` fires `TurnReset` but deliberately **never `TurnStarted`** — the turn's actor already played it. Restoring a snapshot calls `AiController.CancelTurn()`; `ResumeTurn()` hands the turn back.
- Editor: **Tools ▸ Action History**. Page Up / Page Down step back and forward — plain keys because the editor claims Ctrl/Cmd+Z for its own undo. Bound twice: in `ActionHistory.Update` (fires only while the **Game view** has focus) and as a `[Shortcut]` on the window (fires while the window has focus, rebindable under Edit ▸ Shortcuts).

### AI

`Gameplay/AI/AiController.cs` drives a team on `TurnStarted`: per unit, attack the closest reachable enemy, else advance on the closest visible enemy, else move to uncover unexplored map; hands back via `ToggleCurrentTeam()`. Coroutine-paced by `actionDelay`, capped by `maxActionsPerUnit`. `aiEnabled` is live-toggleable (`ToggleEnabled` context menu) to play the AI team manually.

### UI

UI Toolkit throughout (`.uss` at `Assets/`, world-space panels for health bars / AP bars / floating text). `ActionsPointsBar` shows committed vs. previewed cost as separate blob counts, which is how move previews read as "this will cost you N".

## Editor tooling

`Assets/Scripts/Editor/History/ActionHistoryWindow.cs` — the action list (Tools ▸ Action History). Owns no state: it finds the running `ActionHistory` with `FindFirstObjectByType` (like `InGameSelectionMirror`) and polls its `Version`, which survives domain reloads and play-mode changes without re-subscribing.

`Assets/Scripts/Editor/WatchDashboard/` — a persistent watch window. `WatchBoard` is a ScriptableObject (survives recompiles and play-mode toggles) holding `(target, serializedPropertyPath, label)` entries picked from inspector context menus.

**Odin caveat, important for any editor work here:** `InspectorConfig.asset` sets `defaultEditorBehaviour: 11`, so Odin draws *every* user MonoBehaviour/ScriptableObject and **suppresses Unity's `contextualPropertyMenu` and `CONTEXT/Component` hooks**. Only built-in types (e.g. Transform) keep Unity's inspector — the telltale symptom is "the context menu only works on Transform". Two approaches that do work, both used by WatchDashboard:

1. **Inside Odin inspectors** — a generic `OdinValueDrawer<T>, IDefinesGenericMenuItems` at `[DrawerPriority(DrawerPriorityLevel.WrapperPriority)]` whose `DrawPropertyLayout` just calls `CallNextDrawer(label)` (draws nothing), implementing `PopulateGenericMenu`. Generic over `T`, so it applies everywhere. See `WatchOdinContextMenu.cs`.
2. **Menus Odin never touches** — `[MenuItem("GameObject/…")]` and `[MenuItem("Assets/…")]`, building a `GenericMenu` and calling `ShowAsContext()`. The GameObject variant fires once per selected object, so debounce on `EditorApplication.timeSinceStartup`. See `WatchMenu.cs`.

## ImToolkit package

`Packages/com.duxaeternus.imtoolkit` — a local immediate-mode debug UI layer over UI Toolkit, replacing `OnGUI`/`GUILayout` overlays. Call `IM.Label` / `IM.Button` / `IM.Slider` from any `Update()`; no UXML, USS, PanelSettings or scene setup. Layout scopes (`IM.Window`, `IM.Row`, `IM.Box`, `IM.Scroll`) are `using` blocks. Each call advances a cursor through a retained node list, reconciled at end of frame via a player-loop hook.

Two behaviours to know: **clicks report one frame after the press**, and widgets are **keyed by title/label** — pass the optional `id:` argument when label text is dynamic or call order changes between frames, or state will attach to the wrong widget. See the package README for the full API and the IMGUI migration table.

## Conventions

- Namespaces do **not** always mirror folders — action types live in `Actions` while their infrastructure is in `Runtime.Gameplay.Actions`, and both appear in the same files. Follow the file you are editing.
- Systems are wired by explicit `Setup(...)` injection, not `FindObjectOfType` or singletons-by-static.
- State snapshots are cloned into `ChangeEvent<T>`; observers get values, not live references.
- Prefer `[Tooltip]` on designer-facing serialized fields — the existing traits and AI settings are documented that way.
- `gitattributes` (no leading dot, at repo root) configures LFS and `unityyamlmerge` for Unity YAML.
